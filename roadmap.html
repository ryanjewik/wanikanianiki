Kanji Workshop · what to build next

From working code to a working app

Almost everything is written. What is missing is the setup that turns it into something you can open on your phone — and that gap is smaller than the feature list suggests.

00 · where things stand

Two gaps, both of them plumbing

The app has every screen. The backend has all eight endpoints, the WaniKani client with its rate limiter, the sync worker, and 23 passing tests. None of it has ever touched a database or run on AWS, because two setup steps were never done:

  • No migrations. models.py describes five tables. Nothing has ever created them — there is no Alembic setup and no create_all call anywhere.
  • No deployment. lambda_handler.py is written against AWS resources that do not exist. No template, no Dockerfile, no CI.

Neither is a feature. Both are an afternoon. Clearing them converts everything already built into a real app, which is why they come first and why nothing else is worth starting until they are done.

phase 1

Make it real

Get the existing code running against real datathe whole point

No new features. This phase only removes the two things standing between what you have already built and an app you can actually use.

  1. Set up Alembic with the async template — alembic init -t async. Point env.py at Base.metadata and read the URL from get_settings(). The dependency is already declared; nothing else exists.
  2. Write the first revision covering the five existing models plus vocab_items and vocab_sources. Autogenerate, then read it before applying — autogenerate reliably misses server defaults and constraint changes.
  3. Stand up Postgres and migrate. Use the provider's direct connection string for migrations and the pooler for the app; transaction-mode poolers and DDL do not mix. config.py already rewrites either URL for asyncpg.
  4. Backfill and verify. POST /api/sync/backfill, then POST /api/sync, then check GET /api/dashboard against what wanikani.com shows you. This is the first time the cache path has ever run.
  5. Fix the Mangum lifespan issue — a module-level @lru_cache get_client(), and skip aclose() / dispose_engine() when settings.is_lambda. Small, and it has to land before real traffic or the rate limiter is decorative.
  6. Write a SAM template for api-fn and sync-fn off one CodeUri, with the EventBridge schedule and ReservedConcurrentExecutions: 1 on the sync function — which turns a docstring warning into an enforced property. Deploy.
  7. Point the app at it. Set EXPO_PUBLIC_API_URL in mobile/.env and run a real lesson and a real review end to end.

What you get: the app on your phone, showing your actual WaniKani data, with a streak that starts accumulating from the first review you answer through it.

do not skip step 1 with create_all

Base.metadata.create_all() would get you through today in one line. It creates missing tables and silently ignores existing ones — so the second schema change does nothing at all, with no error, until a query fails in production. Six more tables are coming.

phase 2

Photo import

Build the endpoints the app already callsmedium

import.tsx is finished and calls POST /api/vocab-sources, which returns 404 because it does not exist. Closing that gap is what fills vocab_items — and without vocab there is nothing for phase 3 to schedule.

  1. Decide the shape first — see the conflict below. It changes what you build.
  2. POST /api/vocab-sources — accept the multipart image, store it, write a vocab_sources row.
  3. The vision call — prompt for structured JSON with the three textbook columns kept separate, not one blob of text. Layout-aware extraction is the whole reason this beats classic OCR.
  4. POST /api/vocab-sources/{id}/confirm — commit the rows the user kept after correcting them, skipping anything already in the deck rather than duplicating it.
  5. An ocr_handler in lambda_handler.py plus its queue, if you take the asynchronous route.

What you get: photograph a textbook page, correct the readings, and the words land in your own deck.

a conflict to resolve before writing code

uploadVocabPhoto() in api.ts is typed to return { sourceId, items } — the detected rows come back in the upload response. That means a synchronous vision call with the phone holding the connection for 30 to 60 seconds. Behind API Gateway that exceeds the integration timeout outright; behind a Function URL it fits, but it is a poor thing to ask a phone on mobile data to do.

I would change the client. Return { sourceId, status: "pending" } immediately, do the vision call in ocr-fn, and let import.tsx poll until the rows appear. Your schema already assumes this — vocab_sources.status is pending | processed | failed, which is a job table. It is a small change to api.ts and the loading state in import.tsx.

phase 3

Your own SRS

SM-2 for everything WaniKani does not ownmedium

WaniKani items keep WaniKani's stage — mirrored, never recomputed. Imported vocab needs scheduling of its own, and it needs to exist first, which is why this follows phase 2 rather than leading it.

  1. The srs_state table, with skill_type splitting recognition from production so the two schedule independently.
  2. The SM-2 implementation — ease factor, interval, repetitions. Pure functions over a state record, so it tests without a database, the way mapping.py does.
  3. A due-queue endpoint for non-WaniKani items, kept as a separate track from the WaniKani queue — the user is never shown a blended list.
  4. Flashcard review for imported vocab, reading and writing the same srs_state row that generated questions will later use.

What you get: the words you photographed come back on a schedule, without touching WaniKani.

phase 4

Generated practice

Questions, bundles, and the verifierlarge

The other endpoint the app already calls — /api/lesson-bundles/next — and the first piece that needs a second Lambda with a genuinely different runtime shape.

  1. questions and lesson_bundles, with verified defaulting to false.
  2. The generation agent in a generate_handler, drafting 3–5 bundles at a time. Context is recently passed WaniKani items plus your imported vocab — not the full history.
  3. The verifier gate. Never serve a question with verified = false. This is the rule that makes generated content safe to study against.
  4. The stock-check trigger — EventBridge runs one cheap query ("fewer than three unconsumed bundles, and new material since last time?") and enqueues generation only when both hold. The clock triggers the decision, not the spend.
  5. GET /api/lesson-bundles/next, which also enqueues a top-up when stock is low, so heavy study days do not wait for the next tick.

What you get: practice questions that target what you are actually learning, generated ahead of you so they are there offline.

phase 5

Grammar intake

The Obsidian connectorlast, deliberately

Your own notes are firm that this is optional: the connector is opt-out entirely, grammar_topics can simply be empty, and the generation prompt treats it as an optional context block. Its only consumer is the phase 4 agent — building it earlier means building an input for something that cannot read it yet.

  1. Explicit file selection at setup — one read file, one write file. Not a vault scan.
  2. The grammar_topics cache, refreshed whenever the connector reads.
  3. Opt-out write-back, disableable independently of reads.
  4. Fold topics into the generation prompt as optional context.

What you get: questions that exercise the grammar you just studied, not only the vocab.

if you only do one thing

Start with the migration

Everything else in phase 1 is blocked on it, and it is the smallest of the seven steps. Four commands and a file you read before applying: 

cd backend
alembic init -t async migrations
# edit migrations/env.py: import Base from app.db.models,
# read the URL from app.config.get_settings()
alembic revision --autogenerate -m "initial schema"
alembic upgrade head

Add vocab_items and vocab_sources to models.py before you autogenerate, so they land in the same first revision. That one decision is what keeps phase 2 from starting with a data migration.

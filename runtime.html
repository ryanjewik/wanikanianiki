Kanji Workshop · backend architecture

What wakes the backend

Four Lambda functions off one artifact. Nothing runs between requests, nothing installs at invocation, and each function is woken by a different signal.

01 · the components

Four functions, one codebase

Every box below is a separate Lambda function with its own memory, timeout, concurrency limit and trigger — but all four are the same app/ package, deployed once. Only the entry point differs.

Function Entry point Woken by Config Status
api-fn lambda_handler.handler A request from the phone, via Function URL 512 MB · 30 s built
sync-fn lambda_handler.sync_handler EventBridge, on a clock 512 MB · 5 min · concurrency 1 built
ocr-fn lambda_handler.ocr_handler A queued photo job 1 GB · 2 min planned
generate-fn lambda_handler.generate_handler A queued generation job 1 GB · 15 min · concurrency 1 planned
02 · how a function starts

Cold start, warm start, freeze

The dependencies are already inside the artifact before the first request ever arrives. Lambda downloads and unpacks; it never resolves or installs anything. That work happened on your machine or in CI, at deploy time.

the short answer

Opening the app wakes api-fn only. EventBridge wakes sync-fn on its own schedule with the app closed. SQS is not something the app opening triggers either — it is how api-fn hands slow work to another function without making the phone wait.

03 · a wrinkle in your code

Where process-level setup actually belongs

The INIT block in the diagram above is the only place that runs once per container. Anything you want shared across warm invocations — a connection pool, a rate limiter — has to live at module scope to land there.

FastAPI's lifespan looks like the right home for it, and under uvicorn it is. Under Mangum it is not. In mangum/adapter.py, the LifespanCycle is constructed inside __call__, and its __enter__ / __exit__ run startup and shutdown — so both fire on every single invocation, not once per container.

what this costs you today

main.py's lifespan builds the shared WaniKaniClient and closes it again. Per request, in Lambda, that means a brand-new RateLimiter with an empty window, a fresh httpx pool, and a dispose_engine() call. Every request believes it owns the full 60/min budget — the exact failure the docstring in main.py warns about.

Harmless at one user. It becomes real the moment two things run at once.

The fix is to hang it off the module, the same shape as get_settings():

@lru_cache
def get_client() -> WaniKaniClient:
    return WaniKaniClient(get_settings())

deps.wanikani_client then returns that instead of reading app.state, and the lifespan skips aclose() and dispose_engine() when settings.is_lambda is true — the flag already exists in config.py. Under uvicorn nothing changes. Under Lambda the client finally lives as long as the container does.

sync-fn is unaffected: it builds its own client with async with WaniKaniClient() and never touches Mangum.

04 · why a queue and not a call

The photo upload never blocks the phone

A vision call takes thirty seconds or more. If api-fn waited for it, the phone would wait too, and the request would sit there burning Lambda time doing nothing. So the HTTP function writes a row, drops a message, and returns — the slow function wakes up on its own.

Your schema already assumes this: vocab_sources.status is pending | processed | failed, which is a job table.

05 · what "not always on" actually means

The idle bill

Lambda is genuinely zero when nothing is happening. The pieces that are not zero are worth knowing about, because they are what "always on" really costs you.

  • The four functions — nothing. No invocations, no charge.
  • The artifact at rest — cents. S3 storage, or ECR if you go the container route.
  • EventBridge — the schedule itself is free; you pay for the invocations it causes, so a longer interval is a real lever.
  • Postgres — the one thing that does not truly scale to zero. Neon suspends and resumes automatically in well under a second; Supabase's free tier pauses after a stretch of inactivity and needs a manual restore. Check both providers' current terms before you commit — your config.py takes either URL unchanged, so it stays a cheap decision to revisit.
  • No NAT gateway — because the functions stay out of a VPC, per the call already recorded in backend/README.md. That single line item would have cost more than everything above combined.
